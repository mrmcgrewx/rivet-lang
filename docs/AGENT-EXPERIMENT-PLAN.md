# Same-model language authoring pilot

User request: agents independently solve the same problems in Rivet, C and Rust using the same model; compare correctness, retries, token usage, runtime and memory. Existing completed baseline is `57188a5`, with native optimization implementation `c279276`. Do not change the language/compiler/runtime or existing benchmark/source examples during this experiment.

## Design fixed before trials

- Nine fresh-context workers: one for each language × problem pair. Problems are Two Sum (including subquadratic search), Add Two Numbers (actual linked lists), and Median of Two Sorted Arrays (logarithmic search). Use the published LeetCode constraints and the same input/output values across languages. This is one sample per cell, a pilot rather than a statistical ranking. Familiar LeetCode problems may be represented in model training.
- Workers use `collaboration.spawn_agent` with `fork_turns: none`, inheriting the same model and reasoning setting. Read each worker's own session metadata afterward and require identical model/effort across all nine. Current parent records identify `gpt-6-astra`, effort `xhigh`; verify actual worker settings rather than assuming inheritance.
- Each receives the same task instructions, public examples, submission policy and generic I/O contract, plus its language-specific API/format documentation. Rivet requires its binary-format specification; that additional reading and byte-writing tool work counts toward its usage. C uses the C standard library; Rust uses the standard library and safe Rust. No downloaded dependencies, network lookup, existing repository solutions or cross-worker communication.
- Each worker owns only its isolated workspace outside the repository and gets no chat history. Do not read the repository examples, source-authoring script, prior algorithms, benchmark solutions or other worker files. Isolation is procedural and audited through tool commands, not an OS security boundary. All workers receive the same available tools and common restrictions.
- Rivet authors a real `.rvb` source. A local Python byte writer is allowed as an authoring tool and must be retained. It may encode numeric records/resolve labels but cannot execute the algorithm or hide a C/Rust/Python solver. C/Rust author only their solver against supplied generic input/output scaffolding. No algorithm-specific scaffolding or language changes.
- Three formal submissions maximum: initial candidate and up to two repairs. All compilation/execution/testing must go through the coordinator's submission command, which snapshots the candidate before building and records the result. No unrecorded compiler/interpreter/test runs. Edits and byte-generation commands before a submission are not separate retries. Stop on the first development-suite pass or after three submissions. Feedback is compiler diagnostics or the first failed development case; no coordinator algorithm coaching.
- The coordinator freezes public development and withheld holdout corpora before workers start. Workers cannot inspect the grader or withheld corpus. After workers stop, holdout results do not trigger repairs. Report first-submission and final development outcomes, holdout pass counts and complexity/representation audit separately; do not count a passing sample as full correctness.
- Agent self-reported token counts are not used. Extract numeric `token_count` usage and model/effort metadata only from the nine child sessions identified by exact parent/thread paths. Publish input, cached input, uncached input, output and reasoning-output subset separately; input is cumulative over model calls, and cached tokens are part of input. Do not add reasoning twice, infer billing, copy session contents, system instructions or reasoning text. Keep command-only audit evidence scoped to this experiment. The coordinator/setup/review tokens are excluded and disclosed.

## Interfaces and acceptance

All use signed 64-bit input values. Native wrappers handle stdin and serialization; Rivet's ordinary generic read/return operations perform the corresponding boundaries. Domain-valid inputs only are scored. Native parsing time is included in the process metric, excluded from the preloaded solver metric.

| Problem | Input / output | C solver | Rust solver |
| --- | --- | --- | --- |
| Two Sum | `n values... target`; two distinct indices, either order | `Pair solve(const int64_t *, size_t, int64_t)` | `solve(&[i64], i64) -> (usize, usize)` |
| Add Two Numbers | Two count-prefixed reversed-digit lists; digit list result | `Node *solve(const Node *, const Node *)` | `solve(&Option<Box<Node>>, &Option<Box<Node>>) -> Option<Box<Node>>` |
| Median | Two count-prefixed sorted arrays; finite numeric median | `double solve(const int64_t *, size_t, const int64_t *, size_t)` | `solve(&[i64], &[i64]) -> f64` |

C `Pair` contains two `size_t` fields; `Node` contains `int64_t value` and `Node *next`. Each returned C node must be individually heap allocated and owned by the caller, without input aliasing. Rust's supplied `Node` has `i64 value` and `Option<Box<Node>> next`. Agents may use their language's general-purpose structures; C's lack of a standard hash map is part of this practical language/tooling comparison. Audit expected subquadratic Two Sum, linear list addition and logarithmic median search; parsing/preloading is separate. The experiment is not a matched-data-structure microbenchmark or a claim of equivalent language safety.

Coordinator provides frozen compiler/CLI, header/node definitions and wrappers. C solver and driver compile as separate translation units at Clang `-O3`, no LTO or fast-math. Rust solver is a separate rlib with `-C opt-level=3 -C overflow-checks=yes -C panic=abort -C lto=off`; driver links that library with the same settings, with black-box inputs/outputs in the timing loop. Forbid unsafe Rust. Rivet uses its existing speed profile with all checks. Holdout C correctness also runs under address/undefined-behavior sanitizers; sanitizer timings are excluded.

## Harness preparation delegation (not measured authoring workers)

Before the nine fresh trials, two helpers may implement generic measurement scaffolding. Their usage is coordinator/setup overhead and excluded from the authoring comparison. They must not write trial solutions. C harness owner: `experiments/agent-language-v1/harness/driver.c`, `c_backend.c`, and `docs/AGENT-EXPERIMENT-C-HARNESS.md`. Rust harness owner: `experiments/agent-language-v1/harness/driver.rs` and `docs/AGENT-EXPERIMENT-RUST-HARNESS.md`. Coordinator owns headers, Rivet adapter, all Python orchestration/oracles/corpora, packets, snapshots and shared docs. No helper Git mutations.

`harness/backend.h` fixes the C driver/backend interface; `api.h` fixes C solver types. Compile `TASK=1/2/3`. The Rust driver compiles with `--cfg task="two_sum"`, `"add_two_numbers"`, or `"median"`; it calls a separate `solution` rlib's public `entry` with the solver signature above. The coordinator supplies `Node` at the solution crate root for task 2 and appends a `#[inline(never)]` entry wrapper around the worker's `solve`. The C backend owns ordinary input nodes and calls the separately compiled worker solve. Rivet's adapter implements the same backend interface against production runtime values.

Default driver mode reads one task input from stdin and prints a JSON integer array or finite scalar. `--bench POOL ROUNDS WARMUPS MODE` loads a pool where the first token is case count, followed by each task's normal input and then `expected_length expected_values...`; median expectation is one integer equal to twice the median. `MODE` is `evaluate` or `control`. Validate individual answers in a preflight pass before warmup/timing. Normalize the unique Two Sum pair order; compare exact digit vectors or twice-median value. Generic output checksum: start uint64 1469598103934665603, fold answer length then each normalized int64 value with `hash = (hash XOR uint64(value)) * 1099511628211` wrapping at 64 bits. Median folds `[2 * median]`. A round sums each hash times `(1 + index % 17)` with wrapping; the final checksum is the wrapping sum over rounds. Control reads a volatile/black-box expected hash; never subtract it.

Time repeated solve, output capture/hash and per-query cleanup with a monotonic clock. Do not parse/print inside the timed interval. JSON output fields: `mode`, `cases`, `rounds`, `calls`, `warmup_calls`, `elapsed_ns`, `checksum`, `expected_checksum_per_round`, `ticks_per_case` (zero for languages without fuel). Bound pool to 256 cases, at most 100000000 timed calls, warmups <=10000; reject malformed benchmark arguments. Preserve normal input/output ownership; call backend finish after timing. Native driver and backend compile separately from the solver with strict C warnings. Rust uses safe code, `black_box` around solver arguments/results and explicit wrapping checksum arithmetic. The harness contributes overhead; report it and test it independently before trial launch.

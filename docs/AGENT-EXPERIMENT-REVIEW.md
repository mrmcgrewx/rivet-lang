# Independent authoring-pilot review

Reviewed the frozen protocol, harness, corpora and packets at `7461e96`, and the nine submitted programs and measurements preserved at `eb39fdc`. This review is unmeasured preparation/verification work: its tokens and additional tests do not belong to the nine authoring trials. The reviewer changed only this document and did not repair solvers, change the frozen harness, rerun performance measurements or mutate Git.

**Result: no blocking correctness, protocol or measurement finding in the inspected pilot.** The evidence supports the reported outcomes for these programs, cases and host. It does not establish a general language ranking. Supplementary CI AddressSanitizer results, clean-checkout reproduction and actual workbench verification remain the coordinator's final acceptance responsibilities; this review does not substitute for them.

## Independent checks performed

- Verified every frozen manifest and packet hash, deterministic regeneration of the committed corpus, and all submitted source/byte-writer hashes against their formal submission records.
- Independently checked the constraints and expected results of all **988 corpus records**: 30 development, 878 holdout and 80 performance cases across the three problems. Two Sum used sorted two-pointer search rather than the grader's pair enumeration/value counting; addition used positional integer reconstruction; median used the standard-library median operation. The generated cases agree with the grader's oracles.
- Reconciled all **690 raw performance observations**, including wrapping checksums, call counts, per-call divisions and positive Rivet fuel counts. Recomputed every published runtime/RSS summary from its seven selected measurements. No control or startup subtraction was applied.
- Reconciled all nine numeric usage records: identical `gpt-6-astra` / `xhigh` configuration, completed sessions, monotonic cumulative counters, cached-input inclusion, uncached-input subtraction and reasoning-output inclusion. Checked the scoped command-audit hashes. Raw session transcripts and reasoning were neither read nor exported by this review.
- Inspected all **43 command-only tool-call records** and the retained sources. Each worker made exactly one formal submission; commands stayed within packet reads, owned source/handoff edits, permitted Rivet byte generation, submission and submission polling. No prior-solution lookup, external dependencies, network use, manual compiler/test run or post-pass solver edit was found. This is a procedural audit, not an OS-enforced isolation claim.
- Ran **576 additional native correctness checks**, using a separate deterministic seed: 64 new cases per problem against each of the three frozen executables. These included duplicate-rich Two Sum inputs, arbitrary-size valid reversed-digit operands and small duplicate-rich sorted arrays. All passed. These reviewer tests are separate from the frozen 878-case holdout score and do not create authoring retries.
- Re-executed each of the three retained Rivet byte writers in a temporary directory. Each reproduced the submitted `.rvb` byte-for-byte. The writers encode instruction records and labels; they do not execute the input problem or substitute a Python solver.

## Algorithm and boundary assessment

All three Two Sum programs check the complement among prior values before insertion, preventing element reuse. Their expected linear hash-table searches satisfy the task's subquadratic requirement. C and Rivet use open addressing, while Rust uses the standard `HashMap`; this is not a comparison of matched hash functions, table layouts or adversarial-input guarantees. Rivet's map allocation has a fixed 32,768-slot capacity, whereas the C and Rust choices scale their reservations from the input.

All addition programs traverse actual linked nodes, compute one digit and carry at a time, and create owned output nodes. C and Rust append result nodes with constant auxiliary state. Rivet's immutable prepend-only nodes require an intermediate reversed chain and another traversal to construct the final order. Its extra nodes and work are real properties of this submitted implementation and available language operations, not hidden work in the runtime adapter. All satisfy linear time; Rivet uses additional linear temporary storage beyond the returned list.

All median programs use logarithmic partition search and constant search storage. The C worker chose a lower-bound search that loads fewer boundary values during each iteration; Rust and Rivet chose different two-direction partition searches. Consequently their runtime ratios mix algorithm-expression choices, generated code, runtime checks and harness overhead. The known input bounds make Rivet's domain-external sentinels valid; all actual array accesses are guarded. The empty-array, odd/even and duplicate cases checked here agree with the required result.

The preloaded Rivet transformation changes only named input/output/cleanup/entry boundaries. Its reverse transformation restores the original LLVM exactly, with all generated tick call sites retained. The accepted programs consume their two inputs before query allocation, so the adapter's upfront restoration of the input logical charge preserves the relevant allocation accounting. Real runtime allocation cleanup and fuel reset run after each query; retained immutable inputs are freed after measurement. The generic adapters do not implement any of the three task algorithms.

C and Rust solvers are separately compiled from their drivers, with no LTO. Rust's non-inlined entry and black-box boundaries, C's external calls, actual output capture, preflight comparison and timed checksums provide appropriate protection against eliminating the measured work. The preloaded interval includes solve, capture, normalization, hashing and result cleanup. Its control loop is a measurement floor, not a complete estimate of wrapper overhead.

## Limits that must accompany the results

1. There is **one authoring sample per language/problem pair**. Seven timing samples do not create seven independent agent solutions. All nine first-submission successes leave retry behavior unmeasured beyond the observed zero retries, and familiar LeetCode tasks may already be represented in model training.
2. Additional Rivet specification reading and byte-writer construction are part of the measured authoring workflow. C and Rust benefit from established model familiarity and standard libraries. The comparison measures these practical workflows, not a trained-to-equal-familiarity language experiment.
3. Input tokens include cached input. Cache residency is not controlled, and the first Rivet trial has substantially more uncached input than its later trials. Report input, cached input, uncached input and output together; do not treat uncached totals alone as an intrinsic language-efficiency or billing ranking. Reasoning tokens are an output subset. Coordinator, harness and review usage are excluded.
4. Runtime results describe the submitted implementations on this machine. Different hash maps, median variants, list ownership, checks and capture paths prevent attributing every difference solely to the language or compiler. C is not given Rivet's safety contract, and safe Rust still differs from Rivet's bounded runtime semantics.
5. Peak RSS is per-child **whole-process** memory, including setup, retained inputs, preflight and warmup. It is not auxiliary algorithm storage or incremental solver allocation. C retains parsed list arrays plus contiguous input nodes; Rust uses boxed input nodes and discards the parsing arrays; Rivet retains its tagged runtime values. Report process and preloaded scopes separately.
6. The documented local ASan initialization hang was an infrastructure failure reproduced by an empty program. Local UBSan success must not be labeled local ASan success. The independent Linux CI sanitizer results are additional correctness evidence and must not enter the Apple Silicon runtime/RSS comparison.

The frozen sources and raw evidence are suitable for publication with these qualifications. A broader conclusion would require more independent agent runs, less familiar tasks and explicit control or separate reporting of cache state, data structures and safety semantics.
